## AMD CBS / memory controls

After removing extractor metadata/noise, the HII/IFR content of `CbsSetupDxeRPL` is semantically identical across 1.12, 1.15 and 1.17. `AodDxe` is also semantically stable.

The hidden tuning surface retained in newer firmware includes primary/secondary/tertiary DRAM timings, RTT/ODT, drive strengths, Power Down, TSME, memory training, ECC, address hashing, fabric-clock and voltage controls.

The original community 1.12 modification is therefore best understood as an **access/visibility unlock**, not an implementation of new memory-training features.

### Important limitation

A hidden HII question can only expose functionality that the underlying firmware/AGESA/SMU actually implements. Making a question visible does not create a missing hardware/firmware capability.

## Save / Restore User Defaults

All three versions contain real AMI actions:

```text
Save as User Defaults
Restore User Defaults
Load Optimized Defaults
```

`Save as User Defaults` and `Restore User Defaults` are nested under an unconditional suppression expression:

```text
SuppressIf
    Uint64 Value: 0x1
```

The detailed extracted context is preserved under `evidence/hii/user-defaults.txt`.

### Interpretation

This establishes the presence of a hidden **single AMI user-default save/restore mechanism**. It does not establish multiple named OC-profile slots.

## Above 4G Decoding

1.12 contains two `Above 4G Decoding` questions pointing at the same underlying setting (`VarOffset 0x9D`):

- one normally exposed entry;
- a second entry already buried under always-true suppression.

In 1.15 and 1.17, the visible copy is gone while the suppressed copy remains.

This directly demonstrates the 1.14 changelog item:

```text
Hide Above 4G Decoding
```

Focused IFR evidence is in `evidence/hii/above-4g-decoding.txt`.

## AMD Variable Protection

`AmdPbsSetupDxe` gains the following question by 1.15:

```text
AMD Variable Protection
```

Properties:

- VarStoreId: `0x1`
- VarOffset: `0x91`
- default: Enabled
- help text explicitly says it protects AMD CBS/PBS/AOD variables against runtime modification by tools such as RU.

A corresponding new executable module `AmdVariableProtection.efi` is present by 1.15.

This is a real released behavior change not explicitly listed in the known 1.13–1.15 changelog. It may be part of the PI 1.0.0.3h platform update, but that attribution is not yet proven.

Focused evidence is in `evidence/hii/amd-variable-protection.txt`.

## 1.17 TCG Storage Security setup addition

By 1.17, setup contains two `TCG Storage device Security Configuration` forms and a new VarStore associated with `TcgStorageDynamicSetupVar`. They accompany new executable modules `TcgStorageSecurity.efi` and `SmmTcgStorageSec.efi`.

No known 1.16/1.17 changelog line explicitly mentions this feature, so it is currently tracked as a confirmed released change with undocumented provenance.

## DRFXI 1.17 clean unlock implementation

The version-aware clean-unlock branch is now statically implemented and validated.

The community `795iX3D.bin` reference was rechecked against stock 1.12. Its decompressed `AMITSESetupData` differs in exactly 60 one-byte positions and every difference sets only access bit `0x04` (`01->05`, `09->0D`, or `29->2D`). Public `UEFI-Editor` source independently identifies the same byte as the AMITSE access-level field and provides stable semantic record keys based on IFR QuestionId/Prompt/Help identifiers.

The first DRFXI 1.17 patch intentionally applies a smaller target set:

- 13 question/reference records covering the UMC/DDR memory path;
- 9 form records covering the corresponding parent forms plus `SMU Common Options`, which makes the already-present VDDP/FCLK branch reachable;
- 2 `Setup` IFR constants, changing only the outer unconditional suppressors for `Save as User Defaults` and `Restore User Defaults` from `Uint64(1)` to `Uint64(0)`.

Total semantic edits before recompression: **24 bytes**.

The patch is generated by `scripts/patch_drfxi_117_clean_hii_unlock.py`, which accepts only the exact official 1.17 image SHA-256, validates the target Setup PE32 and SetupData payload hashes, locates the target records semantically rather than by whole-image offsets, and repacks the two nested LZMA containers without changing any FFS/section allocation.

Reference output SHA-256:

`dc70d7d94d146fa3a8f75233f729648695dba07eef7245514121e2fffe7d879f`

Static validation found:

- identical UEFIExtract A75 structural reports for stock and patched images;
- `6926` extracted leaf files in each image with identical relative path sets;
- exactly two differing leaf payloads: `Setup` PE32 and decompressed `AMITSESetupData`;
- exactly 2 differing bytes in `Setup` PE32;
- exactly 22 differing bytes in `AMITSESetupData`;
- patched IFR differs semantically only in the two intended `Uint64 1 -> 0` instructions;
- every other extracted leaf is byte-identical, including NVRAM/default stores and the rest of the executable/data/ACPI corpus.

See `docs/findings/clean-hii-unlock.md` and `data/drfxi-1.17-clean-hii-unlock-validation.json` for the full target set and validation record.

This is a **statically validated research image, not a flashing recommendation**. Hardware boot/runtime behavior and flash-path/recovery safety remain untested.

## Unlock strategy implications

The demonstrated safe research approach is **semantic and version-specific**:

1. identify the same HII questions/forms in the target release;
2. patch only the target release's access/suppression metadata;
3. avoid copying a whole SetupData blob or fixed offsets from 1.12 into 1.17;
4. preserve firmware container sizes/structure where possible and validate the resulting image recursively;
5. treat static structural correctness separately from actual flash safety or runtime functionality.

The community `795iX3D.bin` remains useful only as an example of intent; its complete SPI image contains donor-board runtime state and is not suitable as a clean patch source.
