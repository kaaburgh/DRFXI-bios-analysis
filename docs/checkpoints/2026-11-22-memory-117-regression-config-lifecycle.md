# DRFXI 1.15 -> 1.17 DDR5 regression: configuration / training lifecycle and closure of static explanations

Date: 2026-11-22 (work started 2026-11-17)

Scope: continue `2026-11-14-memory-117-regression-static-narrowing.md`. Find a causal mechanism for the BD790i report ("after 1.17 the previous manual timings gave memory errors/BSOD; Auto became much looser, tRFC ~968, tWR 96; some previously reachable values no longer worked"), or exclude the static explanations and name the narrow missing information. Static analysis only: no flashing, no variable writes, no runtime experiments.

The Reddit thread could not be fetched from this environment (site blocked); the report is used as summarised in the task. It remains a single-system anecdote about a **BD790i**, not a BD790i X3D.

## 0. Result in one paragraph

No data or code that computes, selects, trains or applies DRAM timings or DRAM-side voltages differs between 1.15 and 1.17 (**CONFIRMED** across the whole image, sections 2–7). What the firmware *does* do, identically in both versions, is treat a BIOS update performed with the shipped command as a **full memory-configuration and training reset**: `/N` reprograms NVRAM, `AmdSetupRPL` falls back to StdDefaults with sync-generation `[0x08]=0`, `CbsSetupDxeRPL` detects the mismatch with APCB token `0xB331378E` on the next boot, purges every CBS (purpose-3) APCB token and rewrites only non-Auto values, flushes the APCB, and the APCB driver marks the saved memory context as discarded, so ABL trains from scratch; Memory Context Restore is **effectively enabled by the platform default** although Setup shows "Auto", so whatever the fresh training produced is then reused on every boot. This chain explains "much looser Auto values" (they are SPD/JEDEC-derived Auto values) without any 1.17 change, and gives a concrete, testable route by which "the same manual timings" can stop being stable: they now run on a different training result and without any setting the owner did not re-enter. The only 1.17-specific behaviour on this lifecycle is new: `OemDxe` writes an APCB token (iGPU configuration) and flushes it when the dGPU state changes, which forces one more full retrain; it does not touch timing tokens. `STABILITY_BOOST` is a no-op for stock settings (the byte sent to the SMU is identical).

Confidence: high that 1.17 contains no memory-algorithm/data change; high that the update resets configuration and training; medium that this lifecycle (plus incomplete re-entry and training variance) is the explanation of the BD790i observation — that last step needs hardware data (section 10).

## 2. Closure: every 1.15 -> 1.17 delta is classified

`evidence/memory-117/04-module-classification.txt`:

- PCD name table (by name): four tokens added (`LanRootPortAslName`, `PcdReduceHardwareEnable`, `WLanRootPortAslName`, `PcdCfgSmuStabilityBoost` = 0x496); all later tokens shift by +1…+4. **95** same-size modules differ **only** by these shifts (verified per byte against the name-derived shift map).
- The remaining **27** same-size residuals are all classified: build timestamps (`0105101023 -> 081c110d25`), one shared flash-library routine (Smbios/SmiFlash/Rpmc/PrepareWhiteList + FlashDriver/FlashDriverSmm), HII string-id shifts (`FboGroupForm`), Setup DEPEX (TCG), two 256-byte key/signature blobs, `AmdCcxZen4Dxe` (token computed as `0x400-k`, same +3 shift), `CrbDxe`/`CrbPei` (function returning the BIOS version `0x10F -> 0x111`), `AmdCpmOemInitPeim` (GPIO table reordered, identical entry set), and the NVRAM store (section 3).
- Size changes / additions: `OemDxe`, `SmuV13Dxe`, `ReFlash`, `Setup`, `AMITSE`, `AmiAgesaAcpi`, PCD DB, AMITSE setup data, `Recovery`, two ACPI tables; new `AmdCpmOemAcpi`, `TcgStorageSecurity(+Pei)`, `SmmTcgStorageSec`.
- Memory path: `AmdMemFl1Pei`, `AmdSocFl1RplPei`, `AmdMemRestorePei`, `AmdAgesaParameterGroupPei`, `AmdMemoryHobInfoPeimRpl`, `AodPei`, `PcdPeim` (both PEI copies), `AmdMemRestoreDxe`, `AmdMemFl1Dxe`, `CbsBaseDxeRPL` are **identical**; `AmdMemRestoreDxeV2`, `AmdApcbDxeV3/SmmV3`, `ApobRplDxe`, `CbsSetupDxeRPL`, `AodDxe/AodSmm`, `AmdPspDxeV2Rpl` are **PCD-renumbering-only**.
- AMD part (`02-…`): ABL0, PMU firmware (3 code/data pairs), microcode, SMU firmware, PSP OS are identical; the three APCB blobs differ only in `UniqueAPCBInstance` + checksum; payload hashes identical (`03-apcb.txt`).

Consequence: anything 1.16 introduced and 1.17 kept is inside this list. A memory-path change from 1.16 would have to be reverted in 1.17 to be invisible, so the missing 1.16 image cannot hide a *persisting* memory delta (**CONFIRMED** as a logical consequence of the closure).

## 3. A — flash -> NVRAM -> effective settings

1. **The shipped NVRAM area contains only `StdDefaults`** (no `AmdSetupRPL`, `AodSetupRpl`, `AMD_PBS_SETUP`) in both images (`05-nvram-and-defaults.txt`). `/N` ("Program NVRAM") therefore leaves the board with defaults unless something preserves setup. **CONFIRMED** (image content).
2. **No setup preservation is in play.** The command has no `/SP`. AFU 5.16.01's newer preservation (`preserveconfig.cpp`, PLDM via OFBD, `/CLRCFG`, `/BCPALL`) requires firmware support; no 1.15/1.17 module carries a PLDM/BCP handler (string search over every module; the only `Bcp` hit is an incidental byte sequence inside a 640 KiB RAW data blob, FFS `3dd936f6-…`; only the generic OFBD core `Ofbd.efi` exists). **STRONG EVIDENCE** that settings are not preserved by AFU (not proven without executing AFU).
3. Defaults are identical: `AmdSetupRPL` StdDefaults byte-identical; CBS IFR (574 questions) and AOD IFR (118 questions) identical in layout, defaults and ranges (`06-…`). The only StdDefaults change is the removal of the 7-byte `Setup` of GUID `80e1202e-…`, which is the **ReFlash** varstore (`Reset NVRAM`, `Boot Block Update`, both default 1 in 1.15; questions removed in 1.17) — firmware-side recovery/capsule flashing, not the AFU path. **CONFIRMED.**
4. **Boot-time CBS resync** (`08-cbs-fingerprint-resync.txt`): on every boot `CbsSetupDxeRPL` reads APCB token `0xB331378E` and compares it with the stored generation id `AmdSetupRPL[0x08]`. On mismatch (or a failed read) it computes a MurmurHash3-style fingerprint over 88 CBS fields, stores it in `[0x08]`, and runs the full CBS→APCB sync. StdDefaults have `[0x08]=0`, so **the first boot after an NVRAM reset always resyncs**. Executing the extracted fingerprint routine on the StdDefaults gives `0x4B9D5809`, exactly the value of `0xB331378E` in the shipped override APCB (same routine and result in 1.15 and 1.17). **CONFIRMED.**
5. Variable attributes/versioning: `OemDxe` writes `AmdSetupRPL` with attributes `0x7` and the full 0x6D5 buffer obtained by `GetVariable`, changing only offset 0x44; the structure size (0x6D5) and question layout are unchanged between versions, so there is no structure-version migration to get wrong. **CONFIRMED** (code + IFR identity).
6. Out-of-band edits (setup_var-style, AMISCE, efivar writes) change `AmdSetupRPL` without touching `[0x08]` or the APCB token, so they are not pushed to the APCB by the boot path; only a Setup "Save" (direct call after `SetVariable`) or a generation mismatch pushes them. **STRONG EVIDENCE** (call-site analysis). Relevant to anyone tuning without the Setup UI.

Not established: which flash areas AFU rewrites under `/B /P /N /K /L` (the AMI ROM-layout attribute bits are not public; the AFU help separately lists a "Program PSP block" option that the command does not use). Because of item 4, CBS overrides end up consistent with the reset variable either way; the residual unknowns are APOB-NV and AOD (purpose-2) token survival (section 4, H5).

## 4. B — APCB / APOB / training persistence / Memory Context Restore

- **APCB is a derived cache of setup.** `CbsSetupDxeRPL` sync (`07-cbs-to-apcb-token-map.txt`, 89 tokens): acquire (`+0x60`), **purge all purpose-3 tokens** (`+0xC0`, dl=3), then `SetBool/8/16/32` (dl=3) only for non-Auto values, then flush (`+0x08`) and release (`+0x68`). Protocol member offsets were confirmed against the function table of `AmdApcbDxeV3` (`.data @0xA160`). Map identical in 1.15 and 1.17. **CONFIRMED.**
- **APCB flush discards the memory context.** In `AmdApcbDxeV3` the flush member (`+0x08`) reaches the routine at `0x3F10`, which prints `[AMD MemRestore] Discard current memory context (for APCB update)` and sets bit 0x02 or 0x08 of extended-CMOS index 0x0D (ports 0x72/0x73) depending on a CPUID check; `Set8`, purge, acquire and release do not reach it (`09-…`). The next ABL run therefore performs full training. **CONFIRMED** (call graph + code); the ABL-side consumption of the CMOS bit is inferred from the log text (**STRONG EVIDENCE**).
- **Memory Context Restore is effectively ON by default.** Setup "Memory Context Restore" defaults to Auto (0xFF) and is skipped by the sync, so the platform value in the main APCB applies: token `0xFEDB01F8 = TRUE` (priority 0x20, board 0xFFFF). Identical in both versions. **CONFIRMED** that the platform default is TRUE; that ABL treats it as "enabled" is the natural reading (**STRONG EVIDENCE**). The UI showing "Auto" is therefore *not* the effective state.
- **APOB NV** (saved training, flash `0x125000`, 160 KiB) is blank in both images; it is populated at runtime. If the flash rewrites it, training restarts; if not, the APCB flush above (always triggered on the first post-update boot by the resync) discards the context anyway. Either way the first post-update boots train from scratch. **STRONG EVIDENCE** (both branches traced; which one applies depends on AFU coverage).
- **`UniqueAPCBInstance`.** fiano documents it as ensuring compatibility "for a given flashed BIOS life cycle"; every acquired release rotates it (1.04…1.17) while 1.07→1.12 and 1.15→1.17 keep identical payloads. It is an expected per-build marker for invalidating build-bound state, not evidence of a memory change. Its exact consumer is inside ABL (not analysed). **INFERENCE** for the precise role; **CONFIRMED** that it is not a 1.17-specific signal.
- **New in 1.17: `OemDxe` writes the APCB.** After setting `AmdSetupRPL[0x44]` it calls `Get8/Set8(0x1FB35295 = iGPU configuration, purpose 3)` and the flush member, then resets via CF9h (`10-…`). The flush is the member that discards the memory context, so each dGPU appear/disappear transition costs one extra full retrain (plus the reset). It does not purge or rewrite timing tokens. **CONFIRMED** (code path); effect on stability: only via an additional fresh training (**INFERENCE**).

## 5. C — Auto timings, manual overrides, UI vs effective values

- **Gating** (`07-…`): a timing token is pushed only if `Active Memory Timing Settings [0x116] == Enabled` **and** the per-timing `Ctrl == Manual`. `Memory Target Speed` needs only the master gate. With the master gate at its default (Auto) no timing token is written, regardless of the per-timing Ctrl fields. **CONFIRMED.**
- **Auto** = token absent → ABL computes from SPD/JEDEC (ABL identical). The numeric fields (e.g. `Twr` default 48, `Trfc1` 50) are *not* what Auto applies; they are stored placeholders. **CONFIRMED** for the gating; ABL's Auto algorithm is unchanged (identical binary).
- **Units**: CBS/AOD timings are MEMCLK cycles (tCK = 2000/MT·s⁻¹ ns). `Twr` range is 48..96, `Trfc1` 50..4095 (both menus). The reported Auto pair tWR 96 / tRFC 968 is 30.0 ns / 302.5 ns at DDR5-6400, i.e. ordinary SPD-derived Auto values at a high data rate (`13-timing-arithmetic.txt`). The owner's own 1.15 values (tRFC 480 at 6000) are 160 ns. **CONFIRMED** arithmetic; the reporter's data rate is unknown.
- **Two menus, one token set**: AOD (`AodSetupRpl`, AMD Overclocking) holds its own timing fields plus `UCLK DIV1 MODE`, `VDD Misc`, `SoC Voltage`, `DIMM VDD/VDDQ`, `Power Down`; `AodSmm` writes the same APCB token IDs with purpose 2, after calling protocol member `+0xD0` with purpose 2 and a 59-token list (most likely a purge of exactly those tokens; member semantics inferred, not executed). CBS purpose-3 tokens sit in override instance 1 (priority mask 0x04), purpose-2 instance 0 has mask 0x10, platform defaults 0x20. With fiano's level enumeration (HardForce=1 … Default=6) CBS would outrank AOD where both set a value. **INFERENCE** (purpose→instance mapping and priority ordering not executed).
- **Reset-to-default**: StdDefaults for both variables are identical in 1.15/1.17; `AodSetupRpl` and `AMD_PBS_SETUP` are not in StdDefaults and are recreated by their drivers. **CONFIRMED** for CBS; AOD driver defaults unchanged with the identical IFR (**STRONG EVIDENCE**).

## 6. D — SMU, PCD, voltages, late initialisation

- `SmuV13Dxe`: the only executable change besides renumbering is reading PCD 0x496 (`PcdCfgSmuStabilityBoost`, name from the PCD name table) into byte `+0x4DF` of the 0x594-byte SMU configuration structure and printing it. The PCD is a zero-initialised DXE dynamic token; no module in 1.17 loads `0x496` as an immediate except `SmuV13Dxe`; the structure template (copied before fields are filled) is identical in 1.15 and 1.17 and holds 0 at `+0x4DF`. With the default PCD the table sent to the SMU is byte-identical at that offset. **CONFIRMED** for stock settings (a computed-token setter is not exhaustively excluded but none exists as data or immediates).
- No voltage-related PCD default, AOD/CBS voltage question or SMU firmware changed (sections 2, 5). `TcgStorageSecurityPei` (new) and the S3 PME/link ACPI changes act on storage/PCIe. **CONFIRMED** no DRAM-voltage path change.
- Anything in DXE runs after training; it could only matter through (a) values handed to the SMU (unchanged), or (b) a forced retrain (the `OemDxe` APCB flush). It cannot change Auto timing values.

## 7. E — platforms and releases

- One image, one main APCB. Board-masked memory types exist for board mask `0x0002` (board ID 1) alongside `0xFFFF`: SMBus DIMM-info and one other type are byte-identical to their `0xFFFF` twins; the 4-entry SPD block is entirely marked `SpdValid=0, DimmPresent=0` (inert placeholders). No other board/CPU-specific memory data exists. **CONFIRMED** that BD790i and BD790i X3D receive the same memory policy from firmware data.
- 7945HX and 7945HX3D share the Dragon Range IOD/UMC; firmware memory code is the same Dragon Range FL1 AGESA image in both cases. Silicon (IMC/DIMM) margins are per unit and not knowable from firmware.
- No AGESA/PI update is claimed: ABL/PMU/APCB payloads are identical, so there is no evidence of a DragonRangeFL1PI change between 1.15 and 1.17. ComboAM5PI is not involved.

## 9. What transfers from BD790i to BD790i X3D

Transfers (same image, same code, same data): the update resets CBS/AOD settings and training, MCR is effectively on by default, the CBS gating and Auto behaviour, the `OemDxe` dGPU path, and the absence of any 1.17 memory-algorithm change.

Does not transfer: that the X3D system's previously stable DDR5-6000 profile will fail on 1.17. Nothing in the firmware predicts different behaviour of the same complete configuration on 1.17; what it predicts is that the configuration must be fully re-entered and re-validated on a fresh training. The reporter's kit, data rate, voltages and re-entry steps are unknown, and memory-controller margin is per unit.

## 10. Most informative read-only checks on real hardware

All are reads; nothing writes variables or flashes. Tool: `scripts/fwtools/memory_state_report.py`.

1. **On 1.15 now** (baseline): export `AmdSetupRPL-3a997502-647a-4c82-998e-52ef9486a247`, `AodSetupRpl-5ed15dc0-edef-4161-9151-6014c4cc630c` and `AMD_PBS_SETUP-a339d746-f678-49b3-9fc7-54ce0f9df226` from efivarfs, and save the current SPI image with the flash utility's save-ROM function. The report shows which timing tokens are *actually* in the APCB (effective manual values), the sync-generation state, MCR/Power Down/gate states and whether APOB NV is populated. This is the complete record needed to re-enter the configuration after any update.
2. Record the running timings/clocks (e.g. a ZenTimings-style readout) and WHEA/corrected-error counters after a cold boot, for the same baseline.
3. **If/when updating** (owner's decision): repeat 1–2 after the first boots on 1.17, before and after re-entering settings. Distinguishes H1/H2 (variables reset, APCB rebuilt, APOB NV state) from a true 1.17 difference and tests H5 (AOD tokens/APOB NV surviving, i.e. AFU coverage).
4. The single discriminating datum for "1.17 computes Auto differently": Auto timings at the **same** target speed on 1.15 and on 1.17. Static analysis predicts identical values.
