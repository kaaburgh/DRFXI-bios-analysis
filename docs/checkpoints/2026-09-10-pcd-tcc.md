# DRFXI 1.12 → 1.15 — PcdPeim RAW database semantic-diff checkpoint

Date: 2026-09-10

Scope: **only** the early PEI `PcdPeim` external RAW PCD database. The goal was to normalize token renumbering and determine whether a changed scalar default explains the 1.15 changelog item `Set TCC to 100`.

## Inputs

```text
1.12 PcdPeim RAW database
size:   5696
SHA256: 8d68393cb1388c3c936a24116883c0f8991f22696fc5e6d06980e096fd97668c

1.15 PcdPeim RAW database
size:   5704
SHA256: e4847fe7ead968ced7c2842bd2e20934c3220765d53a606b35bca85ce94a8435
```

Both identify as EDK II `PCD_DATABASE_INIT` BuildVersion 7.

## Format and normalization

The RAW section matches the EDK II external PCD database layout: a 16-byte PCD database signature GUID, build/length/SKU fields, and offsets to `ExMapTable`, `LocalTokenNumberTable`, `GuidTable`, `StringTable`, `SizeTable`, and optional name tables.

A `LocalTokenNumberTable` entry encodes PCD type, datum type and data offset. For `PCD_TYPE_DATA`, the low offset bits point to the scalar default. Offsets beyond `Length` refer to the zero-initialized UnInit database area allocated by PcdPeim at runtime.

Header comparison:

```text
                         1.12      1.15
Length                   5696      5704
UninitDataBaseSize        776       778
LocalTokenCount           963       966
ExTokenCount               40        40
GuidTableCount              5         5
LocalTokenTableOffset    0x298     0x298
ExMapTableOffset         0x158     0x158
GuidTableOffset          0x11A4    0x11B0
StringTableOffset        0x122C    0x1238
SizeTableOffset          0x13DA    0x13E6
PcdNameTableOffset          0         0
```

The token-category counts differ only by three BOOLEAN DATA tokens. UINT8, UINT16, UINT32, UINT64 and STRING token counts are unchanged.

All 40 DynamicEx semantic identities `(TokenSpaceGuid, ExTokenNumber)` are identical between the two databases, and **every DynamicEx local token number shifts by exactly +3**. This is a strong independent normalization anchor: three ordinary Dynamic tokens were inserted ahead of the DynamicEx tail; the existing token set was not arbitrarily reordered.

A value-aware sequence alignment excluding physical offsets and local token numbers produces:

```text
equal existing token records: 962
inserted token records:         3
deleted token records:          0
same-category value changes:    1
```

The three additions in 1.15 are ordinary Dynamic BOOLEAN PCDs:

```text
new token 5
  descriptor: 0x011015E5
  default:    1
  initialized in binary

new token 163
  descriptor: 0x01101914
  default:    0
  zero-initialized UnInit area

new token 164
  descriptor: 0x01101915
  default:    0
  zero-initialized UnInit area
```

Because `PcdNameTableOffset == 0`, their source-level CNames are not recoverable from this RAW database alone.

## Key finding: one existing scalar changes 91 → 100

Exactly one pre-existing scalar PCD changes value:

```text
1.12 local token number: 209
1.15 local token number: 212

descriptor in BOTH databases:
0x0400009C

EDK II decode:
PCD type:    DATA
datum type:  UINT32
data offset: 0x9C
```

Raw bytes at database offset `0x9C`:

```text
1.12: 5B 00 00 00 -> 91
1.15: 64 00 00 00 -> 100
```

The descriptor occurs exactly once in each database. Its physical data offset remains exactly `0x9C`; only its local token number shifts, because of the three newly inserted Dynamic tokens.

Neighbouring token records also retain the same semantic type/value sequence after the +3 shift, providing an additional local alignment check.

## Attribution

The 1.15 changelog explicitly says:

```text
Set TCC to 100
```

The PcdPeim database contains exactly one changed existing scalar default, and that value changes exactly `91 → 100`. No other aligned scalar changes to 100.

**High-confidence conclusion:** this Dynamic UINT32 PCD is the static configuration change described by `Set TCC to 100`.

The remaining limitation is nomenclature rather than value localization: `PcdNameTableOffset == 0`, so this binary does not contain the symbolic source-level PCD CName. The exact name and its consuming module/function require a separate consumer trace.

This also resolves the earlier apparent contradiction that `AmdSetupRPL`/CBS `TjMax` defaults are unchanged: the vendor change is in a separate platform Dynamic PCD, not in the user-facing setup-variable default.

## Important interpretation boundary

This finding proves a platform PCD input changed from 91 to 100. It does **not** by itself prove that every supported CPU, especially an HX3D part with its own SMU/fused thermal policy, will have an effective 100°C junction limit. CPU/SMU-specific limits may clamp or override the platform input.

## Confirmed findings

1. Both RAW files are valid EDK II BuildVersion-7 PEI PCD databases.
2. 1.15 adds exactly three ordinary Dynamic BOOLEAN tokens.
3. All 40 DynamicEx identities are preserved and their local token numbers move exactly +3.
4. Among pre-existing scalar PCDs, exactly one default changes.
5. That token retains descriptor `0x0400009C`: DATA / UINT32 / database offset `0x9C`.
6. Its value changes `91 → 100`.
7. This is a high-confidence value-level localization of `Set TCC to 100`.
8. The exact symbolic PCD CName is absent from this binary database.
