## `PT`: main PCIe power-transition table

`PT` is a generated PCIe topology/power template. It contains **58 copies** of the same device-power framework: 58 `_PRW`, `_DSW`, `_PS0`, `_PS3`, and `PWRS` PowerResource blocks.

Every `_PRW` package has:

```asl
Name (_PRW, Package (0x02)
{
    0x02,
    0x04
})
```

Every generated PCIe node also gets `_S0W = 0x04`, `_PR0` and `_PR3` backed by a local `PWRS`.

`_DSW` does not program hardware itself; it logs its arguments and cached `PCSA` state. `_STA` and `_INI`, however, probe real PCI config space, derive ECAM addresses, follow bridges, and initialize device/power state. `PT` is therefore a hardware-discovery template, not merely static descriptions.

## `_PS3`: explicit PME_Turn_Off path

The important generated `_PS3` sequence reads an AMD per-port state and, for a matching root-port condition, invokes `M402` when the low six state bits equal `0x1B`. The table's own debug string labels `M402` as `CpmSendPmeTurnOff`.

Cross-reference into the pre-existing `CPMCMN` table shows that `M402`:

1. maps B/D/F to an internal AMD PCIe-port index via `M401`;
2. selects platform-family-specific SMN/register addresses via `M471`;
3. programs an indirect register at `0x84` with the target device/function;
4. triggers a transition using `0x0100` → `0x0300`;
5. on newer platform-family values waits up to about 2 seconds for bit `0x0400`;
6. reads a per-port register at `M471(..., 4) + 0x294`;
7. waits up to another ~2 seconds for its low six bits to become `0x1F`;
8. restores temporary trigger/register state.

The caller records `DPSA = 0x43` for the subsequent D0 transition.

The exact AMD state-machine meanings of `0x1B`, `0x1F` and marker `0x43` remain unresolved.

## `_PS0`: WakeLink + link-training wait

On the matching D0 transition, `_PS0` checks `DPSA == 0x43`, clears the marker, calls `M403(..., One)`, and polls byte `DADR + 0x6B` until `(value & 0x28) == 0x20` or a bounded loop expires. The loop is `0x13BB` iterations with `Stall(0x63)`, approximately 500 ms maximum.

Firmware debug strings identify this as:

```text
CpmWakeLink (..., 1)
Check DL_ACTIVE
CpmWakeLink (..., 0)
```

`M403` in `CPMCMN` maps B/D/F to an AMD port register and sets/clears bit 22 at a platform-derived base `+0x280`.

The resulting exact two-sided handshake is:

```text
enable WakeLink bit
        ↓
wait up to ~500 ms for link active / not training
        ↓
disable WakeLink bit
```

This is substantially stronger evidence for an S3/resume workaround than the original string-only observation.

## Template patching: `GPP5`, `GPP0...H`, `_E10`

A static DSL read is misleading because `AmdCpmOemAcpi.efi` patches the AML before installation.

The PE code locates OEM Table ID `PT` and replaces the placeholder NameSeg `GPP5` with a platform-provided PCIe root-port name. Therefore a mismatch between raw `GPP5` and the base DSDT does not prove the special `_PS3/_PS0` branch is dead.

The same dynamic behavior is clearer in `GPP_PME_`.

## `GPP_PME_`: dynamically retargeted PCIe PME GPE handler

The raw table contains:

```asl
Method (_E10, 0, NotSerialized)
```

with 21 logical port branches:

```text
GPP0 ... GPP9
GPPA ... GPPH
GP17
GP18
GP28
```

For each relevant port it:

1. checks the per-port `ETP*` value;
2. reads PCI config register `0x78` and extracts event/status bits;
3. proceeds for values `1` or `3`;
4. checks the ACPI device exists;
5. sends `Notify(port, 0x02)` (`Device Wake`);
6. sleeps 100 ms;
7. reads the full dword at config offset `0x78`;
8. if bits `0x00030000` remain set, writes the dword back;
9. rereads and may repeat that status-clear write once.

For GPP0 and GPP7, an additional platform condition can issue `Notify(..., Zero)` (`Bus Check`) first.

`M645(bus,dev,fn)` resolves to normal ECAM address construction:

```text
M083 + (bus << 20) + (device << 15) + (function << 12)
```

### Runtime patching

`AmdCpmOemAcpi.efi` builds an 0x58-byte / 22-dword patch array. Twenty-one values map the logical PCIe port NameSegs to platform-provided names. The 22nd patches `_E10`.

The driver reads MMIO `0xFED8025C`, extracts `(register >> 8) & 0x1F`, converts the value to two hexadecimal ASCII digits, and constructs `_Ehh`, replacing the raw `_E10` with the hardware-selected edge GPE method name.

Thus the installed AML is actively specialized to the board/platform's real GPE and PCIe namespace.

## `EXTGPP00`

This table adds wake metadata for GPP0 and GPP2:

```text
GPP0.APRW = Package { 0x08, 0x04 }
GPP2.BPRW = Package { 0x02, 0x04 }
```

It can add `PWR1` resources to placeholder devices, with `_S0W = 4` and `_PR0/_PR2/_PR3 -> PWR1`. It also defines `_GPE` helpers that can send Device Wake notifications to GPP0/GPP2.

No other static AML references to several of these helper names were found across the successfully decompiled 1.17 ACPI corpus, suggesting conditional/template use or C-side patching. The exact activation path remains unresolved.

## `GPIO`

The fourth new SSDT adds `GPIO._AEI` / `GPIO._EVT` handling and an event path that calls `M31D()` then sends `Notify(\_SB.UBTC, 0x80)` (`Status Change`). Current classification: likely bundled GPIO/USB-Type-C integration, not the core PCIe S3 workaround.

## Relation to existing DSDT

The ordinary DSDT still contains older level-triggered GPE handlers that send Device Wake notifications to PCIe GPP nodes. The new `GPP_PME_` therefore adds a separate, dynamically selected **edge-triggered** GPE path rather than simply replacing all existing `_Lxx` behavior.

## Causal assessment

### High confidence

The new 1.17 `AmdCpmOemAcpi` package contains a real PCIe transition framework absent from the 1.15 ACPI corpus.

The strongest S3-relevant sequence is:

```text
D3 transition (_PS3)
    ↓
check AMD per-port state == 0x1B
    ↓
CpmSendPmeTurnOff
    ↓
wait for AMD per-port state -> 0x1F
    ↓
record DPSA marker
    ↓
later D0 transition (_PS0)
    ↓
set CpmWakeLink bit 22
    ↓
wait up to ~500 ms for PCIe DL_ACTIVE / training complete
    ↓
clear CpmWakeLink bit
```

In parallel, a dynamically patched `_Exx` handler processes PCIe port events, sends Device Wake notifications, and acknowledges/clears status at PCI config offset `0x78`.

This is code-and-AML-level evidence, not merely a correlation between S3-related strings and a module name.

### Medium/high confidence attribution to 1.16

The known 1.17 changelog item concerns graphics/iGPU/dGPU behavior. The PCIe PME/D3/D0/WakeLink framework is not naturally explained by that.

The immediately preceding 1.16 item is `Workaround abnormal restart after S3`, making this new ACPI/CPM framework the strongest candidate for that workaround.

### Remaining proof gap

Without the 1.16 binary, it cannot be proven temporally that the package first appeared in 1.16 rather than as an undocumented addition in 1.17.

Still unresolved:

- exact runtime root-port names replacing raw templates;
- symbolic AMD register names for state values `0x1B` / `0x1F`;
- exact C-side activation path for `EXTGPP00`;
- whether every RAW SSDT is installed on BD790i X3D in every boot configuration.
