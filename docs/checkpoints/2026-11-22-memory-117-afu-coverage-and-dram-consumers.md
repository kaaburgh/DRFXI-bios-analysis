# DRFXI 1.15 -> 1.17 DDR5 regression: AFU flash coverage and all DRAM-setting consumers

Date: 2026-11-22 (follow-up to `2026-11-22-memory-117-regression-config-lifecycle.md`, same day)

Scope: two bounded static questions left open by the earlier checkpoint:

1. Which SPI ranges does the shipped command `/p /b /n /k /r /l /RLC:E` rewrite — in particular the APCB, APOB NV and PSP data?
2. Is there any module, besides the CBS sync already traced, that reads the `AmdSetupRPL` DRAM fields or writes/resets DRAM APCB tokens?

Evidence: `evidence/memory-117/14-…`, `15-…`, `16-…` (and the corrected `08-…`), regenerated by `scripts/fwtools/memory117_evidence.py`. No vendor code is executed any more: the CBS fingerprint and the CBS code defaults are computed by `scripts/fwtools/straightline_eval.py`, which interprets objdump text; its fingerprint results equal the earlier native run (`0x4B9D5809`, `0x5F7BBBF0`, `0xB8A93DB9`).

## Corrections to the earlier 2026-11-22 checkpoint

- **Wrong:** "StdDefaults have `[0x08]=0`, so the first boot after an NVRAM reset always resyncs the APCB (and the resulting flush discards the memory context)."
  **Correct:** `CbsSetupDxeRPL` never uses StdDefaults bytes for a missing variable. Its loader rebuilds a missing variable — or one whose header signature is not `0xFC4053AA` (StdDefaults carry a zero header) — from **code defaults**, whose generation field `[0x08]` is already `0x4B9D5809`. With the image APCB in SPI (token `0xB331378E = 0x4B9D5809`) there is **no** automatic resync and no CBS-side APCB flush on the first post-update boot.
- **Changed attribution:** the post-update settings reset comes from the flash itself rewriting NVRAM *and* the APCB (section 1); the post-update full training comes from APOB NV being rewritten blank, not from a CBS flush. The end state described before (defaults/Auto, fresh training, MCR effectively on) is unchanged.
- **H5** of the earlier table ("stale AOD tokens / APOB NV survive the flash") is refuted for SPI-resident state; CMOS-resident state does survive (section 3).

## 1. Flash coverage (question 1)

### ROM layout with area GUIDs

FFS `c91c3c17-…` (freeform, sub-GUID `00781ca1-5de3-405f-abb8-379c3c076984`, the ROM-layout HOB/config-table GUID) holds 18 × 40-byte `AMI_ROM_AREA` records (GUID, address, offset, size, type, attributes). It is identical in 1.15 and 1.17. The eleven areas covering `0x0–0x1000000` (AMD/PSP part) have a zero GUID; `0x1000000` is FV_MAIN `4f1c52d3-…`; `0x1BAF000` the ROM-layout FV; `0x1BB0000` a blank 64 KiB area; `0x1BC0000` backup NVRAM `a7edebd8-…`; `0x1BE0000` NVRAM FV `fa4974fc-…`; `0x1C00000`/`0x1E00000` the two PEI FVs `61c0f511-…` (FV_BB).

### SmiFlash block classification (CONFIRMED)

`SmiFlash` (1.17 @0x2950, unchanged in 1.15 — its only 1.15→1.17 difference is in the shared flash-library routine at 0x37EF) copies **all** records, sorts them by offset and assigns the block types AFU works with (`14-…`):

```text
GUID == FV_BB                      -> 0     BOOT_BLOCK   (/B)
GUID == FV_MAIN (5c60f367|4f1c52d3) -> 1     MAIN_BLOCK   (/P)
GUID == fa4974fc | a7edebd8         -> 2     NV_BLOCK     (/N)
attributes & 0x400                  -> 0     BOOT_BLOCK   (/B)
otherwise                           -> 0x80+n NON-CRITICAL (/K)
```

Result: the two PEI FVs are boot block, FV_MAIN is main, both NVRAM areas are NV, and **all eleven AMD/PSP areas plus 0x1BAF000 and 0x1BB0000 are non-critical blocks 0x80–0x8C**. The area `0xC1000–0x1000000` (NCB 0x8A) contains PSP NV data, RPMC NV, APOB NV (`0x125000`), the PSP/BIOS level-2 directories, the APCB blobs (`0x51D400–0x528000`), PMU firmware and microcode.

### What the shipped command therefore writes

`/p /b /n /k` = main + boot block + NVRAM + all non-critical blocks = **all 18 areas, the whole 32 MiB**. AFU's help text defines `/K` as "Program all non-critical blocks" and logs "Erasing/Updating/Verifying NCB Block"; the separate "Program PSP block" option is not used and is not needed to reach these areas. (**STRONG EVIDENCE**: firmware side CONFIRMED; AFU flag semantics from its own strings; AFU-side preservation beyond `/R` SMBIOS and its OA-key handling is not evidenced but AFU itself was not reverse-engineered.)

Consequences right after the update:

| state | location | after flashing |
|---|---|---|
| CBS/AOD/PBS setup variables | NVRAM `0x1BE0000` (+ backup `0x1BC0000`) | gone; only `StdDefaults` |
| CBS/AOD APCB overrides (manual timings, generation id) | APCB `0x51D400–0x528000` | image APCB: no timing tokens, generation `0x4B9D5809` |
| saved training (MCR context) | APOB NV `0x125000` | blank → full training on the first boot |
| PSP NV data / RPMC NV (fTPM) | `0xC1000`, `0xE1000` | blank (side effect: fTPM state expected to reset — **INFERENCE**, and a cheap real-world proxy for this whole result) |
| extended-CMOS state | RTC CMOS, not SPI | **unchanged** (section 3) |

First boot on 1.17: ABL reads the image APCB (Memory Context Restore platform default TRUE, Auto timings), finds no saved context and trains from scratch; `CbsSetupDxeRPL` recreates `AmdSetupRPL` from code defaults, the generation matches, no resync. The owner's first Setup "Save" with re-entered values runs the CBS sync, flushes the APCB and discards the memory context, so the next boot trains again with the new values, which MCR then keeps.

## 2. All consumers of DRAM settings (question 2)

`16-…` lists every 1.17 module that references the `AmdSetupRPL` GUID/name or any of the 55 DRAM-related CBS tokens (offsets 0x116–0x17F plus MCR):

| module | role | status |
|---|---|---|
| `CbsSetupDxeRPL` | only in-image writer of CBS DRAM values to APCB: Setup save (RouteConfig), boot generation mismatch, APCB-recovery reset | CONFIRMED |
| `CbsBaseDxeRPL` | own loader with the same signature check and code defaults (0x934); stores only, reads no DRAM field | CONFIRMED |
| `CbsBasePeiRPL` (32-bit PEI) | of the CBS fields reads only 0x110–0x113 (USB3 Port 2–5); the rest are default stores | CONFIRMED |
| `BctBaseSmmRPL` | SMM duplicate of the whole CBS sync, published only as SMM protocol `147f8bda-da41-45bb-bc9b-827e72dc30a1` (CPUID 0xA60F00/0xB40F00); **no module in 1.15 or 1.17 references that protocol** → not invoked by in-image code | CONFIRMED |
| `AodSmm` | AMD Overclocking apply path: purpose-2 writes of the same token IDs; also hands VDDIO to ABL through extended CMOS (section 3) | CONFIRMED (trigger chain not fully traced) |
| `AmdApcbDxeV3/SmmV3` | MCR token only inside the token-registration whitelist table | CONFIRMED |
| `OemDxe` | offset 0x44 / token `0x1FB35295` only | CONFIRMED |
| `AmdVariableProtection` | variable-policy protection only | CONFIRMED |

No other path reads the DRAM fields or writes DRAM tokens. Identical in 1.15.

### `CbsSetupDxeRPL` boot sequence (CONFIRMED)

Driver entry (0x10C4–0x1129): allocate the `CBSD` private block, HII ConfigAccess (ExtractConfig 0x894, RouteConfig 0xB58 = Setup save → sync, Callback 0xC60), then:

1. **APCB-recovery reset (0xD68).** If the APOB protocol `0de50221-faaa-45ba-90b9-7bcc26ec60cf` (installed by `ApobRplDxe`; member `+0x08` returns the ABL-reported `ApobApcbRecoveryFlag`, byte `+0x65` of the APOB entry) reports recovery, or APCB token `0xB331378E` holds the sentinel `'RECV'` (`0x56434552`; the fingerprint routine is written never to produce it), the CBS buffer is rebuilt from code defaults, resynced to the APCB and written back. This is a **silent "reset all CBS settings" path**; its trigger lives in ABL (use of the backup APCB).
2. **Loader (0xE68).** `GetVariable(AmdSetupRPL)`: missing or wrong size → code defaults; present with a foreign header signature → bytes `0x20..[+4)` migrated over code defaults (a zero header, as in StdDefaults, migrates nothing); matching signature → used as is. Then the generation check (`[0x08]` vs token `0xB331378E`) and, where rebuilt or migrated, `SetVariable`.

Code defaults (`0x3E58`, evaluated without execution): 707 written bytes, header `sig 0xFC4053AA, len 0x2D8, gen 0x4B9D5809`; **every written body byte equals StdDefaults** and StdDefaults are zero wherever the builder writes nothing; identical in 1.15 and 1.17.

## 3. CMOS-resident state that survives a flash (new lead, UNKNOWN effect)

- `AodSmm` writes `AodSetupRpl[0x197]` — **APU VDDIO Adjust** (the question is created at runtime by `AodDxe` code at 0xC5C5: prompt string 367, VarOffset 0x197, so it is absent from the static IFR) — to extended CMOS index `0xA1` (low byte) and `0xA0` (high byte) when `VDDIO Ctrl` (0x192) is Manual or Separate, and does not clear it when the control returns to Auto. Whether ABL applies this CMOS value independently of the APCB/setup state cannot be determined statically (ABL is not readable).
- Also CMOS-resident: the APCB-update discard bits (extended CMOS 0x0D, `AmdApcbDxeV3`) and `OemDxe`'s dGPU state nibble (index 0x66).
- None of these is touched by AFU. A CMOS clear does clear them.

## 5. Read-only checks this adds

1. Owner recollection, no hardware access needed: after a previous DRFXI update with the vendor package, did Windows ask for the BitLocker recovery key or report a reset TPM / Windows Hello PIN? That is the expected visible side effect of `/K` rewriting PSP NV data and directly supports section 1.
2. On the next saved SPI image (`memory_state_report.py`): the override APCB and APOB NV show whether the image or the board's own state is present after an update.
3. Optional, root on Linux: read extended CMOS indexes `0x0D`, `0xA0`, `0xA1` (reading uses the 0x72/0x73 index/data port pair; nothing is written to CMOS contents) to see whether an old AOD VDDIO value is present.

## 6. Remaining unknowns

- AFU's own behaviour beyond the help text (it was not disassembled): a hidden preservation of some PSP entries under `/K` cannot be excluded statically; observation 5.1/5.2 settles it.
- ABL internals: consumers of the CMOS VDDIO hand-off, the discard bits, `UniqueAPCBInstance`, and the conditions for `ApobApcbRecoveryFlag`.
