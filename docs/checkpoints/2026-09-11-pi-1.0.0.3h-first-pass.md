# DRFXI 1.13 `Update PI 1.0.0.3h` — first bounded pass

Date: 2026-09-11

Scope: only the 1.13 changelog item `Update PI 1.0.0.3h`, using DRFXI 1.12 -> 1.15 because 1.13/1.14 binaries are unavailable. Findings across this interval are not automatically attributed to 1.13.

## Starting constraints

- Do not reopen Intel LAN OPROM, TCC, SMU power-limit internals, S3, DMI, GOP/display, flash EIP/TCG storage.
- Do not reverse-engineer all 181 byte-changed PE modules.
- Normalize PCD-token renumbering, relocations, layout/build noise, and global platform constants before treating a delta as semantic.
- Start from the three named PE modules that are present in 1.15 and absent in the 1.12 named-module set, then follow at most one immediate dependency edge.

## 1. `AmdVariableProtection` — genuine new variable-policy consumer

### Direct DRFXI binary evidence

- FFS GUID: `0F411BE5-B10C-4DDA-B28C-868FC24789F8`
- FFS type: DXE driver (`0x07`)
- PE subsystem: EFI boot-service driver (`0x0C`)
- image size: 10,752 bytes
- entry point RVA: `0x10C4`
- version section: `1.0`
- DEPEX contains:
  - `6441F818-6362-4E44-B570-7DBA31DD2453` = Variable Write architectural protocol
  - `13A3F0F6-264A-3EF0-F2E0-DEC512342F34` = PCD protocol
  - `81D1675C-86F6-48DF-BD95-9A6E4F0925C3` = EDKII Variable Policy protocol
  - fallback `AF23B340-97B4-4685-8D4F-A3F28169B21D` = EDKII VarCheck protocol

The module is a consumer rather than the provider of VariablePolicy/VarCheck. It tries Variable Policy first and falls back to VarCheck.

Protected-variable table entries include:

```text
AMD_PBS_SETUP
AmdSetupRPL
AodSetupRpl
```

The module also manages a separate one-byte variable:

```text
AmdVariableProtection
GUID 40578F3D-65EE-49ED-8BC5-5A32BBEAE745
```

At roughly `0x1674..0x1753`, Runtime Services `GetVariable` / `SetVariable` operate on that control variable. `SetVariable` uses attributes `0x26` and chooses one of two embedded authenticated payloads around RVAs `0x2080` and `0x2420`. The payloads contain certificate/PKCS#7-like material.

The module also creates a VirtualAddressChange event and registers AMD setup-variable protection through VariablePolicy or VarCheck.

The already-known new `AmdPbsSetupDxe` HII item `AMD Variable Protection`, VarOffset `0x91`, default Enabled, is therefore backed by a real new protection implementation rather than being only a UI-label addition.

### Was this functionality already in 1.12?

Focused 1.12 searches found:

- no `AmdVariableProtection` variable/name;
- no module of that name;
- generic VariablePolicy and VarCheck infrastructure already present in `NvramDxe`;
- the AMD setup variables themselves already present elsewhere.

So the semantic addition is a new AMD-specific policy consumer/protection layer, not a replacement variable-policy engine.

### Source-family correlation

Public AMD edk2-platforms board descriptions reference:

`AmdCpmPkg/Features/AmdVariableProtection/AmdVariableProtection.inf`

and explicitly call it a variable-protection feature. This corroborates purpose, but does not establish the exact PI revision in which the DRFXI component landed.

## 2. `GenerateTimeBaseVariable` — companion authenticated-payload generator

### Direct DRFXI binary evidence

- FFS GUID: `EDAF7B16-E15D-4A64-9398-E6CAC9F026AF`
- FFS type: Application (`0x09`)
- PE subsystem: EFI application (`0x0A`)
- image size: 692,320 bytes
- entry point RVA: `0x454`
- version section: `1.0`
- no DXE DEPEX

Important strings:

```text
UINT8 mCreatePayload[] = {
UINT8 mDeletePayload[] = {
0x%02X
AmdVariableProtection
```

Its data contains the same target variable GUID as the DXE driver:

```text
40578F3D-65EE-49ED-8BC5-5A32BBEAE745
```

The entrypoint calls the payload-builder twice. The builder combines the `AmdVariableProtection` name, GUID, attributes `0x26`, authentication/timestamp data and crypto material, then prints C arrays named `mCreatePayload` and `mDeletePayload`.

The large crypto/certificate-heavy image is therefore a coherent companion to the much smaller DXE module and is consistent with generation of its precomputed authenticated create/delete payloads.

It is, however, an EFI **application**, not a DXE driver; it has no DEPEX. Static searches found no firmware executable referencing its FFS GUID. The strongest current interpretation is a maintenance/development payload-generation utility carried in the FV, not an automatically dispatched boot component.

No public source for this exact application was found in the bounded search.

### 1.12 comparison

Neither its target variable/name nor an equivalent named generator was found in the 1.12 extracted executable set. Within this scope it is genuinely new alongside the variable-protection feature.

## 3. `HardwareSignatureEntry` — separate AMI FACS hardware-signature feature

### Direct DRFXI binary evidence

- FFS GUID: `B7EE4835-84CE-4B15-BF52-2D11574CE470`
- FFS type: DXE driver (`0x07`)
- PE subsystem: EFI runtime driver (`0x0B`)
- image size: 6,752 bytes
- entry point RVA: `0x2E0`
- version section: `1.0`
- DRFXI DEPEX: `13A3F0F6-264A-3EF0-F2E0-DEC512342F34` (PCD protocol)

Strings:

```text
HardwareConfigData
AmiHardwareSignatureSetupUpdateCountVar
SIO_DEV_STATUS_VAR
```

Relevant GUIDs present in the binary:

```text
43169678-506C-46FE-B32A-FCB301F74FBD  HardwareChange protocol
B80A8E5B-C02A-4A31-AE12-58E46E803E89  HardwareConfigData variable namespace
3677770F-EFB2-43B2-B8AE-B302E9604882  AMITSE before-boot event/protocol
120D28AA-6630-46F0-8157-C0ADC2383BF5  AMI legacy-boot protocol
81C76078-BFDE-4368-9790-570914C01A65  setup-update-count namespace
```

At entry it installs the HardwareChange protocol and registers the same callback for AMITSE before-boot and AMI legacy-boot notifications.

### Strong AMI source-family correlation

A public AMI Aptio source tree contains the same module name and exact FFS GUID in `HardwareSignatureEntry.inf`, with entry point `HardwareSignatureEntryPoint`. `HardwareSignatureManagement.c` describes the feature as:

- installing HardwareChange protocol;
- tracking memory-map/size, PCI, USB, video, disk and selected setup-change state;
- storing `HardwareConfigData` in NVRAM;
- updating the ACPI FACS hardware signature before boot.

The DRFXI strings/GUIDs and entrypoint behavior closely match this source family. The public older INF has a different DEPEX than this DRFXI build, so it is purpose/source-family evidence, not proof of identical source revision.

### Was this functionality already in 1.12?

Focused 1.12 searches found neither the HardwareChange protocol GUID `43169678-...` nor the `HardwareConfigData` string. This appears to be genuinely newly integrated functionality by 1.15, not merely a renamed module.

## 4. First immediate dependency edge: `NvramDxe`

`AmdVariableProtection` consumes the existing VariablePolicy/VarCheck infrastructure, so its immediate provider `NvramDxe` was compared 1.12 -> 1.15.

```text
size both: 82,944 bytes
1.12 SHA256: 2cf4e7db6ad33461ac11a7acf1508280d16de0e470a5534b355db4b2c07779f7
1.15 SHA256: 7be5c9b15096ef310384ec9f6d4b9a9ca5d6e3c7d9803c41562cf2014d500974
```

Only **28 bytes** differ in the entire PE.

Inspected executable differences are PCD-token immediate renumberings, e.g.:

```text
0x2B0 -> 0x2B3
0x377 -> 0x37A
...
0x3E6 -> 0x3EA
0x3E7 -> 0x3EB
0x3E8 -> 0x3EC
```

The remaining multi-byte constant difference encodes build date/time corresponding to the two firmware builds (`2025-02-13 ...` vs `2026-01-05 ...`).

No changed control flow, VariablePolicy/VarCheck method implementation, or new provider semantic was found.

**Negative result:** AMD variable protection was added as a new consumer on top of an effectively unchanged generic NVRAM policy engine.

## 5. Functional clustering

The three modules do **not** form one functional unit.

A coherent two-module cluster is directly established:

```text
GenerateTimeBaseVariable (EFI app)
        |
        | generates authenticated create/delete payloads for
        v
AmdVariableProtection variable
        |
        v
AmdVariableProtection DXE
        |
        +--> protects AMD_PBS_SETUP / AmdSetupRPL / AodSetupRpl
             through pre-existing VariablePolicy or VarCheck
```

`HardwareSignatureEntry` is a separate AMI platform-management feature for hardware-change/FACS-signature tracking. No immediate protocol/variable/dependency edge connects it to the AMD variable-protection pair.

## 6. MMCONFIG / ECAM `F0000000 -> E0000000`

No immediate dependency edge from these modules to the already-established MMCONFIG relocation was found.

- `AmdVariableProtection`: Runtime Variable services, PCD, VariablePolicy/VarCheck and events.
- `GenerateTimeBaseVariable`: authenticated-payload-generation application.
- `HardwareSignatureEntry`: platform hardware inventory/signature using normal firmware services; no evidence that the ECAM constant is part of this feature cluster.

The ECAM relocation remains a separate platform-init delta. It may independently be part of the PI update, but this pass found no basis to combine it with the three-module additions.

## 7. Official AMD evidence for what `1.0.0.3h` is

External AMD evidence substantially improves version identification even though it does not map the three modules.

AMD's security material identifies the Ryzen 7045 / Dragon Range firmware branch as **DragonRangeFL1 / DragonRangeFL1PI** and names version `1.0.0.3h` explicitly.

AMD's February 2026 security bulletin lists:

```text
AMD Ryzen 7045 Series / Dragon Range
CVE-2024-36311
Mitigation: DragonRangeFL1_1.0.0.3h
Release date: 2025-03-18
```

CVE-2024-36311 is a TOCTOU race in an SMM communications buffer that can bypass input validation and cause out-of-bounds SMM access.

This establishes with high confidence that the MINISFORUM changelog's `PI 1.0.0.3h` refers to the **DragonRangeFL1PI 1.0.0.3h platform-initialization release** appropriate to Ryzen 7045, and that this PI revision carried at least one concrete platform-security mitigation.

It does **not** establish that `AmdVariableProtection`, `HardwareSignatureEntry`, the ECAM relocation, or any particular DRFXI 1.12 -> 1.15 delta is the implementation of CVE-2024-36311 or uniquely belongs to 1.0.0.3h.

## Current attribution assessment

### Confirmed across 1.12 -> 1.15

1. A genuine AMD variable-protection feature appears, including a DXE policy consumer and companion authenticated-payload generator.
2. A separate AMI HardwareSignature/FACS hardware-change service appears.
3. Generic VariablePolicy/VarCheck support predates both and its immediate `NvramDxe` implementation is semantically unchanged after normalization.
4. The previously known MMCONFIG relocation remains a separate platform-init change at the examined dependency depth.
5. Official AMD documentation identifies `DragonRangeFL1PI 1.0.0.3h` as the relevant Ryzen 7045 PI branch/version and shows it as the mitigation level for CVE-2024-36311.

### What can be attributed to `Update PI 1.0.0.3h`?

High confidence:

- the version string in the MINISFORUM changelog corresponds to AMD Dragon Range PI `1.0.0.3h`, not an arbitrary vendor-local numbering scheme;
- that upstream PI release is a meaningful platform/security update.

Not proven:

- that either new feature cluster landed specifically in DRFXI 1.13 rather than 1.14/1.15;
- that `AmdVariableProtection` was introduced by DragonRangeFL1PI 1.0.0.3h;
- that AMI `HardwareSignatureEntry` is an AMD PI component at all;
- that the ECAM move is a 1.0.0.3h change;
- that any inspected delta implements CVE-2024-36311.

Confidence that `AmdVariableProtection` + generator is part of the broader platform update: **medium**.
Confidence for assignment specifically to the `1.0.0.3h` landing: **low-to-medium** without 1.13 or an AMD source/version manifest.

## Stop condition reached

All three new named modules are classified. They do not form one common functional cluster. One coherent AMD variable-protection subcluster is established; `HardwareSignatureEntry` is independent; the first relevant dependency edge (`NvramDxe`) is normalized negative.

Further work on this exact pass would require broad platform-module classification, so the bounded pass stops here.

## Next narrow direction

The strongest evidence-driven next step for the PI line is no longer to inspect arbitrary changed modules. Use the official CVE/version mapping:

1. identify the SMM communication interface/component implicated by CVE-2024-36311 for DragonRangeFL1PI;
2. derive a small candidate-module/GUID set from public AMD/EDK2 evidence before touching DRFXI binaries;
3. compare only the corresponding SMM communication validation functions 1.12 -> 1.15;
4. stop if the upstream component cannot be mapped narrowly without general SMM reverse engineering.

This would test a behavior that is independently known to be present by `DragonRangeFL1PI 1.0.0.3h`, rather than guessing from the 181-module raw diff.
