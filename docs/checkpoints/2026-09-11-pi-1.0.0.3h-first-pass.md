# DRFXI 1.13 `Update PI 1.0.0.3h` — first bounded pass

Date: 2026-09-11

Scope: only the 1.13 changelog item `Update PI 1.0.0.3h`, using DRFXI 1.12 -> 1.15 because 1.13/1.14 binaries are unavailable. Findings across this interval are not automatically attributed to 1.13.

## Starting constraints

- Do not reopen Intel LAN OPROM, TCC, SMU power-limit internals, S3, DMI, GOP/display, flash EIP/TCG storage.
- Do not reverse-engineer all 181 byte-changed PE modules.
- Normalize PCD-token renumbering, relocations, layout/build noise, and global platform constants before treating a delta as semantic.
- Start from the three named PE modules that are present in 1.15 and absent in the 1.12 named-module set, then follow at most one immediate dependency edge.

## 1. `AmdVariableProtection` — genuine new variable-policy consumer

### Direct DRFXI binary evidence

- FFS GUID: `0F411BE5-B10C-4DDA-B28C-868FC24789F8`
- FFS type: DXE driver (`0x07`)
- PE subsystem: EFI boot-service driver (`0x0C`)
- image size: 10,752 bytes
- entry point RVA: `0x10C4`
- version section: `1.0`
- DEPEX contains:
  - `6441F818-6362-4E44-B570-7DBA31DD2453` = Variable Write architectural protocol
  - `13A3F0F6-264A-3EF0-F2E0-DEC512342F34` = PCD protocol
  - `81D1675C-86F6-48DF-BD95-9A6E4F0925C3` = EDKII Variable Policy protocol
  - fallback `AF23B340-97B4-4685-8D4F-A3F28169B21D` = EDKII VarCheck protocol

The module is not the provider of VariablePolicy/VarCheck. Its code first attempts to locate the Variable Policy protocol and falls back to VarCheck when that protocol is unavailable.

The protected-variable table contains at least the following variable names:

```text
AMD_PBS_SETUP
AmdSetupRPL
AodSetupRpl
```

The module also manages a separate one-byte variable named:

```text
AmdVariableProtection
GUID 40578F3D-65EE-49ED-8BC5-5A32BBEAE745
```

Runtime-service calls at approximately `0x1674..0x1753` use `GetVariable` and `SetVariable` for this control variable. `SetVariable` uses attributes `0x26` and selects one of two embedded authenticated payloads around RVAs `0x2080` and `0x2420`.

The two payloads contain X.509/PKCS#7-looking certificate material. The module also creates a VirtualAddressChange event and uses VariablePolicy or VarCheck to register/protect the AMD setup variables.

The already-known new `AmdPbsSetupDxe` setup item `AMD Variable Protection`, offset `0x91`, default Enabled, is therefore supported by a real new runtime protection implementation rather than being only an HII-label addition.

### Was the same functionality already present in 1.12?

Focused 1.12 searches found:

- no `AmdVariableProtection` variable/name;
- no `AmdVariableProtection` module;
- VariablePolicy and VarCheck infrastructure already present in `NvramDxe`;
- the AMD setup variables themselves already existed elsewhere.

Therefore the semantic addition is a **new AMD-specific policy consumer/protection layer**, not a replacement of the generic variable-policy engine.

### Upstream/source-family correlation

Public AMD edk2-platforms board descriptions reference:

`AmdCpmPkg/Features/AmdVariableProtection/AmdVariableProtection.inf`

and explicitly call it the "variable protection feature". This corroborates module purpose, but does not establish which AMD PI release first introduced it or that DRFXI received it specifically in 1.13.

## 2. `GenerateTimeBaseVariable` — companion authenticated-payload generator

### Direct DRFXI binary evidence

- FFS GUID: `EDAF7B16-E15D-4A64-9398-E6CAC9F026AF`
- FFS type: Application (`0x09`)
- PE subsystem: EFI application (`0x0A`)
- image size: 692,320 bytes
- entry point RVA: `0x454`
- version section: `1.0`
- no DXE DEPEX section

Important strings:

```text
UINT8 mCreatePayload[] = {
UINT8 mDeletePayload[] = {
0x%02X
AmdVariableProtection
```

Its data contains the same target variable GUID used by `AmdVariableProtection`:

```text
40578F3D-65EE-49ED-8BC5-5A32BBEAE745
```

The entrypoint calls the payload-building routine twice, once for each mode. The routine constructs authenticated-variable input containing the name `AmdVariableProtection`, GUID, attributes `0x26`, timestamp/authentication structures and then prints the result as C byte arrays named `mCreatePayload` / `mDeletePayload`.

The very large executable contains crypto/certificate machinery consistent with generating the precomputed authenticated payloads embedded in the much smaller DXE driver.

### Interpretation

This is a coherent companion to `AmdVariableProtection`, but it is an EFI **application**, not a DXE driver, and has no DEPEX. Static searches found no firmware module referencing its FFS GUID. The strongest interpretation is therefore a maintenance/development payload-generation utility carried in the FV, not part of the automatically dispatched boot path.

No public source for this exact application was found in the bounded search.

### Was equivalent functionality present in 1.12?

No `AmdVariableProtection` target variable/name or equivalent payload-generator name was found in the 1.12 extracted executables. Within the current bounded search, the generator is genuinely new alongside the protection feature.

## 3. `HardwareSignatureEntry` — separate AMI FACS hardware-signature feature

### Direct DRFXI binary evidence

- FFS GUID: `B7EE4835-84CE-4B15-BF52-2D11574CE470`
- FFS type: DXE driver (`0x07`)
- PE subsystem: EFI runtime driver (`0x0B`)
- image size: 6,752 bytes
- entry point RVA: `0x2E0`
- version section: `1.0`
- DRFXI DEPEX: `13A3F0F6-264A-3EF0-F2E0-DEC512342F34` (PCD protocol)

The binary contains:

```text
HardwareConfigData
AmiHardwareSignatureSetupUpdateCountVar
SIO_DEV_STATUS_VAR
```

and GUIDs:

```text
43169678-506C-46FE-B32A-FCB301F74FBD  HardwareChange protocol
B80A8E5B-C02A-4A31-AE12-58E46E803E89  HardwareConfigData variable namespace
3677770F-EFB2-43B2-B8AE-B302E9604882  AMITSE before-boot event/protocol
120D28AA-6630-46F0-8157-C0ADC2383BF5  AMI legacy-boot protocol
81C76078-BFDE-4368-9790-570914C01A65  setup-update-count namespace
```

At entry it installs the HardwareChange protocol and registers the same callback for the AMITSE before-boot and AMI legacy-boot notifications.

### Strong AMI source-family correlation

A public AMI Aptio source tree contains **the same module name and exact FFS GUID** in `HardwareSignatureEntry.inf`, with entry point `HardwareSignatureEntryPoint`. Its `HardwareSignatureManagement.c` describes the feature as:

- installing the HardwareChange protocol;
- tracking memory-map/size, PCI, USB, video, disk and selected setup-change information;
- storing `HardwareConfigData` in NVRAM;
- updating the FACS hardware signature before boot.

The direct DRFXI strings/GUIDs and entrypoint behavior match this source family closely. The old public INF's DEPEX differs from the DRFXI build, so this is source-family correlation rather than a claim of byte-identical source revision.

### Was equivalent functionality present in 1.12?

Focused 1.12 searches found neither:

- the HardwareChange protocol GUID `43169678-...`, nor
- the `HardwareConfigData` variable string.

Thus this functionality appears genuinely newly integrated by 1.15, not merely renamed.

## 4. First immediate dependency edge: generic variable-policy provider

Because `AmdVariableProtection` consumes existing VariablePolicy/VarCheck services, the immediate provider `NvramDxe` was compared 1.12 -> 1.15.

```text
size both: 82,944 bytes
1.12 SHA256: 2cf4e7db6ad33461ac11a7acf1508280d16de0e470a5534b355db4b2c07779f7
1.15 SHA256: 7be5c9b15096ef310384ec9f6d4b9a9ca5d6e3c7d9803c41562cf2014d500974
```

Only **28 bytes** differ in the entire PE.

The executable differences inspected are PCD-token immediate renumberings, for example:

```text
0x2B0 -> 0x2B3
0x377 -> 0x37A
...
0x3E6 -> 0x3EA
0x3E7 -> 0x3EB
0x3E8 -> 0x3EC
```

The final differing constant in the code/data encodes build date/time:

```text
1.12: 2025-02-13 17:36:02-like build tuple
1.15: 2026-01-05 16:16:23-like build tuple
```

No changed branch, API method, VariablePolicy/VarCheck semantic or new variable-policy provider behavior was found.

**Negative result:** `AmdVariableProtection` was added as a new consumer on top of an effectively unchanged generic NVRAM policy engine.

## 5. Do the three modules form one coherent cluster?

No.

A coherent two-module cluster is now directly established:

```text
GenerateTimeBaseVariable (EFI app)
        |
        | generates authenticated create/delete payloads for
        v
AmdVariableProtection variable
        |
        v
AmdVariableProtection DXE
        |
        +--> protects AMD_PBS_SETUP / AmdSetupRPL / AodSetupRpl
             through pre-existing VariablePolicy or VarCheck
```

`HardwareSignatureEntry` is a separate AMI platform-management feature concerned with FACS hardware signature / hardware-change tracking. No immediate protocol/variable/dependency edge connects it to the AMD variable-protection pair.

The fact that all three appear in the same 1.12 -> 1.15 boundary is insufficient to treat them as one functional unit.

## 6. MMCONFIG / ECAM `F0000000 -> E0000000`

No immediate dependency edge from any of the three new modules to the MMCONFIG base relocation has been found.

- `AmdVariableProtection` is centered on Runtime Variable services, PCD, VariablePolicy/VarCheck and events.
- `GenerateTimeBaseVariable` is a payload-generation application.
- `HardwareSignatureEntry` may inventory PCI configuration as part of its hardware-change checksum, but it consumes normal platform/protocol services; there is no evidence that the ECAM constant is part of this module cluster.

Therefore the existing ECAM relocation remains a **separate platform-init delta**. It may independently be part of the broader PI update, but this bounded pass found no basis to tie it to these new modules.

## Current attribution assessment

### Directly established across 1.12 -> 1.15

1. A new AMD variable-protection feature is integrated, including a DXE consumer and companion authenticated-payload generator.
2. A new AMI HardwareSignature/FACS hardware-change service is integrated.
3. Generic VariablePolicy/VarCheck support was already present in 1.12 and is semantically unchanged in the immediate provider examined.
4. The previously known MMCONFIG relocation is separate from the new-module dependency cluster at this level.

### Can these changes be assigned specifically to `Update PI 1.0.0.3h`?

Not yet.

They are plausible **PI/platform-integration** changes and the AMD variable-protection component exists in modern AMD platform source families. However:

- 1.13 and 1.14 binaries are unavailable;
- no public source/version mapping was found saying that these components first appear in AMD PI `1.0.0.3h`;
- `HardwareSignatureEntry` is AMI platform functionality, not inherently an AMD PI component;
- `GenerateTimeBaseVariable` is a companion utility rather than evidence of a PI core revision by itself.

Confidence that the pair `AmdVariableProtection` + generator is part of the broader platform update: **medium**.
Confidence that it specifically implements the 1.13 `Update PI 1.0.0.3h` line: **low-to-medium** without an intermediate binary or source-version map.

## Stop condition reached

All three new named modules are classified, and they do **not** form one common functional cluster. One coherent subcluster (`AmdVariableProtection` + `GenerateTimeBaseVariable`) is established; `HardwareSignatureEntry` is independent. The first relevant dependency edge (`NvramDxe`) is normalized negative.

Further progress would require either broader platform-module classification or stronger external version evidence, which is outside this bounded pass.
